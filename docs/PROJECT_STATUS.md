## 1. Что это за проект

**RehabGame** — платформа игровой реабилитации руки. Пациент надевает на кисть датчик движения
(плата ESP32-C3 + IMU), наклонами кисти управляет браузерной игрой, а врач удалённо видит
ML-аналитику движений (амплитуда, тремор, плавность, отклонения от личной нормы).

**Стадия:** рабочий сквозной прототип (MVP). Готовится к питчу в программу **ITMLab 3.0** (грант).
В продакшене с реальными пациентами **пока не используется**.

**Цель ценности:** мотивация пациента (игра вместо скучных упражнений) + объективный мониторинг
крупной моторики руки для врача без визита.

## 2. Архитектура и как всё работает

### 2.1 Поток данных (от кисти до дашборда врача)

```
  [ESP32-C3 + IMU]              железо на руке: считает углы наклона (roll/pitch/yaw)
        │  BLE (Bluetooth), строка "yaw,pitch,roll"
        ▼
  packages/ble/                 BleService: подключение, EMA-сглаживание, калибровка нуля,
        │                       клавиатурный fallback (← →) без устройства
        │  событие "data" { smooth (управление), calib (запись), raw (диагностика) }
        ▼
  packages/game-2d / game-3d/   игровой движок: наклон → движение; пишет сырой ряд IMU 25 Гц
        │                       (Space Catcher / Canvas2D, City Driver / Three.js)
        │  onGameOver({ score, imuTimeSeries, ... })
        ▼
  web/ (React SPA)              рисует UI; шлёт результат на сервер; показывает дашборд
        │  REST  POST /api/sessions  (JWT в заголовке)
        ▼
  api/ (FastAPI)                авторизация (JWT), бизнес-логика, ВЕСЬ ML встроен
        │   ├── extract_features() → 14 признаков движения
        │   ├── mark_validity()    → отсев «пустых прогонов»
        │   ├── detect_anomalies() → норма / внимание / критично (+ z-score объяснение)
        │   └── recommendations + narrative
        ▼
  MongoDB (rehabgame)           users, patients, sessions (+ сырой ряд), scores

  ml-service/  — ОТДЕЛЬНО от продакшена: обучение модели + тесты паритета + debug-UI
  tools/       — симулятор/рекордер IMU (тест без железа)
```

### 2.2 Карта модулей

| Модуль | Технология | Роль | Трогать? |
|--------|-----------|------|----------|
| `api/` | FastAPI, Python 3.10+, Beanie ODM | Бэкенд: auth, данные, **ML встроен** | да |
| `web/` | React 18, Vite, Tailwind, Zustand | Фронтенд SPA: игры, дашборд врача | да |
| `packages/ble/` | Чистый ES-модуль | Связь с устройством по BLE | только с прошивкой |
| `packages/game-2d/` | Canvas 2D | Движок Space Catcher | осторожно |
| `packages/game-3d/` | Three.js | Движок City Driver | осторожно |
| `packages/api-client`, `auth` | ES-модуль | **Legacy-reference, не используется** | кандидат на удаление |
| `ml-service/` | Python, scikit-learn | Обучение модели + паритет-тесты | да |
| `tools/` | HTML/JS | IMU-симулятор и рекордер | по необходимости |
| `docs/` | Markdown | 9 документов | поддерживать |

### 2.3 Ключевые архитектурные решения

- **Метрики считаются на сервере, не в браузере** — нельзя подделать, единый источник.
- **Сырой ряд `imu_time_series` хранится навсегда** — топливо для будущего обучения моделей.
- **Игровые движки и BLE без зависимостей от React/DOM/сети** — тестируются в `demo.html`.
- **ML живёт в бэкенде (`api/app/ml/`), «лаборатория» (`ml-service/`) — отдельно.** Цена: **две
  копии логики признаков**, которые держат синхронными вручную + тест паритета (см. §5.2).
- **Patient и User — разные сущности** (пациент существует без своей учётки).
- **LLM строго ограничен** — только перефразирует посчитанные числа, по умолчанию выключен.

## 3. ML-аналитика — 4 слоя разной надёжности

| Слой | Файл | Что делает | Надёжность |
|------|------|-----------|-----------|
| 1. Признаки | `features.py` | 14 чисел из сырого ряда (ROM, тремор, плавность, спектр FFT) | **Высокая** (детерминированно, есть тесты) |
| 2. Аномалии (z-score) | `anomaly.py` | Отклонение от **личной нормы** пациента в σ | **Высокая, честная** — основной механизм |
| 3. Обученная модель | `anomaly_model.joblib` | RandomForest+IsolationForest, вердикт норма/нет | **Низкая** — обучена на 100% синтетике |
| 4. Рекомендации/заключение | `recommendations.py`, `narrative.py` | Советы врачу + текстовое заключение (шаблон/LLM) | Средняя (правила, пороги) |

**Состояние модели (слой 3):** `v6-2026-06-08-spectral-synthetic`, `validation: none`,
`synthetic_only: true`, 14 признаков, ROC-AUC 0.984 — **на синтетике** (label = параметры
генератора, не клиника). Это эксперимент, а не клинический инструмент. Реально «работающий AI» —
слои 1–2.

## 4. Что готово и проверено

- **Сквозной путь работает:** BLE → игра → признаки → ML → дашборд врача.
- **Две игры:** Space Catcher (2D), City Driver (3D, две оси управления — руль + газ/тормоз).
- **Multi-axis анализ:** обе оси City Driver идут в вердикт (модель axis-agnostic, без переобучения).
- **Гард «пустых прогонов»** (`validity.py`): сессии без движения (ROM≈0) не портят аналитику.
- **Импорт легаси-данных из Firebase** в Mongo (идемпотентно, частичные признаки помечены).
- **Демо-режим** (`DEMO_MODE=true`): 5 пациентов с готовыми траекториями для показа без железа.
- **Калибровка старта** (`zeroNow()`): платформа не «уезжает» в начальной позе.
- **Все тесты зелёные** (проверено 2026-06-23):

| Набор | Результат |
|-------|-----------|
| `ml-service/tests/` (паритет признаков) | **10 passed** |
| `api/tests/` (Firebase-импорт, multi-axis) | **15 passed** |
| `web` vitest (фронтенд) | **4 passed** |

## 5. Слабые места, недоработки, проблемы

Приоритеты: **P0 критично · P1 важно · P2 средне · P3 мелко/процесс**.
Помечено `[НОВОЕ]` — найдено в этом аудите. Помечено `✅ ИСПРАВЛЕНО (2026-06-23)` — закрыто в
ветке `feature/dcp-retarget-and-hardening` (см. CHANGELOG).

### P0 — критично

**5.1 `[НОВОЕ]` `✅ ИСПРАВЛЕНО (2026-06-23)` Сломан контроль доступа к данным (IDOR).**
Закрыто: `verify_patient_access()` в `auth/deps.py` применён во всех роутах sessions/insights/patients.
Большинство роутов проверяют только факт авторизации, но **не проверяют, что пользователь имеет
право на этого пациента/сессию**. Любой авторизованный пользователь, зная ID, может прочитать
чужие медицинские данные:
- `GET /sessions/{id}`, `GET /sessions?patient_id=…`, `GET /insights/{patient_id}`,
  `PATCH /sessions/{id}/label` — **нет проверки владения вообще** (`api/app/routes/sessions.py`,
  `insights.py`).
- `GET /patients/{id}`, `PATCH /patients/{id}` — любой **врач** видит и редактирует **чужих**
  пациентов (нет `doctor_id == user.id`; для сравнения `GET /patients` фильтрует правильно).
- `POST /sessions` принимает любой `patient_id` без проверки.

Для медицинского приложения с ПДн это серьёзно. Приложение пока не в продакшене, поэтому это не
«утечка сейчас», но **блокер перед любым реальным запуском** и уязвимость по критерию ITMLab
«Этика и безопасность данных» (10%). Лечится централизованной проверкой владения (зависимость
FastAPI `verify_patient_access`).

**5.2 `[НОВОЕ]` `✅ ИСПРАВЛЕНО (2026-06-23)` Вся работа после v8.6 не закоммичена.**
Закрыто: работа коммитится в ветку `feature/dcp-retarget-and-hardening` (отдельно от `main`).
В git-истории **всего 2 коммита** (последний — «v8.6», предыдущий назван «.»). При этом в рабочем
дереве лежат недели работы: multi-axis (`multiaxis.py`), гард валидности (`validity.py`), фикс
train/serve skew, фронтенд-тесты, 3 новых документа (`HOW_IT_WORKS`, `WORK_PLAN`, `ITMLAB_AUDIT`) —
всё как `modified`/`untracked`. Один сбой диска или неосторожный `git checkout` — и всё потеряно.
Нет точек отката, нет истории изменений в VCS (версии живут только в `CHANGELOG.md`). **Нужно
закоммитить и завести нормальную историю.**

### P1 — важно

**5.3 Обученная модель — на 100% синтетике, без клинической валидации.** (известно, см. доки)
ROC-AUC 0.99 — это «модель угадывает свой генератор», не клиника. Пока главным механизмом должен
быть z-score (слой 2). Реальный путь — обучить на собственных размеченных сессиях.

**5.4 Петля разомкнута: метки боли/усталости собираются, но в обучении не используются.**
Пациент на экране результата ставит метки (это ground-truth норма/аномалия), мост
`mongo_loader.py` готов, но реальных сыгранных+размеченных сессий ещё нет → модель не дообучается.
Блокер — нет данных (нужны живые сессии с поднятой Mongo).

**5.5 `[НОВОЕ]` `✅ ИСПРАВЛЕНО (2026-06-23)` Дрейф второй копии ML: `recommendations.py` рассинхронился.**
Закрыто: `ml-service` синхронизирован с `api`; `.gitattributes` нормализует переводы строк (LF).
`api/app/ml/recommendations.py` содержит логику спектрального тремора (`TREMOR_POWER_HIGH`,
частотный анализ в рекомендации), а `ml-service/app/recommendations.py` — **нет** (старая версия).
Тест паритета (`test_parity.py`) покрывает только `features.py`, поэтому дрейф не ловится. Это
ровно тот техдолг «двух копий», о котором предупреждает архитектура, — и он уже реализовался.

**5.6 `[НОВОЕ]` `✅ ИСПРАВЛЕНО (2026-06-23)` JWT-секрет по умолчанию, без гарда в продакшене.**
Закрыто: предупреждение на старте (`config.is_default_secret` + лог в `main.py`). Переопределяется `JWT_SECRET`.
`config.py`: `jwt_secret = "dev-secret-change-in-production"`. Если развернуть без переменной
окружения — токены подделываемы (любой может выписать себе admin-токен). Нет проверки на старте,
что секрет переопределён. `.gitignore` корректен (секреты не в git), но дефолт небезопасен.

**5.7 `✅ ИСПРАВЛЕНО (2026-06-23)` Нет дисклеймера «не диагноз» и экрана согласия на обработку ПДн.** (P0 по ITMLab, §2)
Закрыто: `components/Disclaimer.jsx` на дашборде врача и экране результата пациента; обязательный
чекбокс согласия в `Register.jsx` + поле `User.consent` + проверка на `/auth/register`.

### P2 — средне

**5.8 Web Bluetooth не работает на iPhone/Safari.** Только Chrome/Edge (ПК) и Android.
Клавиатурный fallback есть в коде, но не оформлен в UI как осознанный путь «без устройства» +
нет понятного сообщения на неподдерживаемом браузере. Удар по критерию «Универсальный дизайн» (25%).

**5.9 `/insights` грузит до 50 полных сессий в память и считает в приложении.** На больших
объёмах (тысячи сессий/пациент) понадобится агрегация на уровне БД. Сейчас не проблема, но не масштабируется.

**5.10 Прошивка не сохраняет сырой ряд (Firebase-устройство пишет только агрегаты).** Поэтому
импортированные сессии «частичные» (3 признака из 14). Полную модель на данных устройства не
обучить без доработки логирования на прошивке.

**5.11 Дублирование ML-логики (`api/app/ml/` ↔ `ml-service/app/`)** — корневой техдолг (см. 5.5).
Кандидат на вынос в общий пакет, чтобы исключить ручную синхронизацию.

**5.12 `[НОВОЕ]` `✅ ИСПРАВЛЕНО (2026-06-23)` `anomaly.py`: разные переводы строк (CRLF vs LF).**
Закрыто: `api/app/ml/*.py` приведены к LF, добавлен `.gitattributes` — обычный `diff` теперь чист.

### P3 — мелко / процесс

- **5.13 Нет реального теста с пользователями** (0 из 15% по ITMLab) — ни одного пациента/врача вживую.
- **5.14 Железо ESP32-C3 + IMU самодельное, не сертифицировано** как медизделие.
- **5.15 Legacy-пакеты `packages/api-client`, `packages/auth`** — «reference», не используются.
  Мёртвый код, кандидат на удаление.
- **5.16 `[НОВОЕ]` Мелкая нестыковка в доках:** `HOW_IT_WORKS.md` говорит «~16 признаков», модель
  и `ML_CONTRACT.md` — 14 (плюс `sampleCount`/`durationSec`/`valid` не идут в модель). Уточнить.
- **5.17 Локализация хранения ПДн под РК** не зафиксирована в архитектуре (нужно для медданных граждан РК).

## 7. Рекомендованные приоритеты

1. **Закоммитить всю текущую работу** (5.2) — 10 минут, убирает риск потери недель труда.
2. **Починить контроль доступа** (5.1) — централизованная проверка владения пациентом/сессией.
3. **Гард JWT-секрета + дисклеймер/согласие** (5.6, 5.7) — дёшево, закрывает «Этику» ITMLab.
4. **Синхронизировать `recommendations.py`** и добавить тест паритета на него (5.5).
5. Собрать первые реальные размеченные сессии → замкнуть петлю обучения (5.4).
6. Оформить путь «без устройства» в UI и сообщение для Safari (5.8).

> Сильные стороны, на которые опираться: честная архитектура ML (надёжное z-score отделено от
> экспериментальной модели), сквозной рабочий прототип, гард валидности, сохранение сырого ряда,
> зелёные тесты во всех трёх наборах.
