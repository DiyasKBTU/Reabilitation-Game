# Калибровка v2 — персональный профиль моторики

> Дизайн-предложение (не реализовано). Цель: превратить калибровку из «дотянись до упора»
> в короткий клинический протокол, который снимает **персональную сигнатуру нарушения**
> ребёнка и делает её точкой отсчёта для всей дальнейшей аналитики.
> Составлено 2026-07-15. Обсудить + сверить с реабцентром (см. `docs/CLINICAL_VALIDATION.md §7C`).

---

## 1. Что не так с калибровкой v1

Сейчас (`web/src/pages/Calibration.jsx`) два шага: **ROM** (дотянуться в 4 стороны) +
**точность** (навести на 5 мишеней). Первая пригодная сессия → `Patient.baselines[game]` =
её `features`. Ограничения:

- Снимает только **диапазон** и грубую точность. Не измеряет **тремор**, **реакцию**,
  **дисметрию** (промах мимо цели), **асимметрию** явно.
- Baseline = обычные игровые `features`, а не прицельный замер. Тремор-признаки по игровому
  ряду недостоверны (рваный BLE + игра гонит цель).
- Нормализация дальнейших сессий идёт от «первой пригодной», а не от **чистого замера покоя/
  усилия** ребёнка. Мы не знаем его личный «пол шума», его собственный уровень тремора.

## 2. Идея v2 — сигнатура вместо одной точки

Каждый суб-тест прицельно измеряет **один клинический конструкт** и пишет чистый ряд.
Из них собирается **`calibration_profile`** — персональный отпечаток, относительно которого
считаются z-scores, пороги тремора и ожидания ROM. Это усиливает то, что уже сейчас в проде —
**личную норму** (главный механизм до клинической модели).

| Суб-тест | Что измеряет | Клинический конструкт | Признаки |
|----------|--------------|-----------------------|----------|
| **1. Покой** (удержание нейтрали 5–8 с) | тремор покоя/позы, «пол шума» датчика | дискинезия, атаксия | `restTremorPower`, `restTremorFreqHz`, `noiseFloorDeg` |
| **2. Активный диапазон** (4 стороны, по осям) | достижимый ROM + **асимметрия** сторон | контрактуры, гемипарез | `rollRom`, `pitchRom`, `rangeAsym` |
| **3. Наведение + удержание** (точка → дотянись → замри 2 с) | реакция, дисметрия, интенционный тремор | атаксия, брадикинезия | `reactionMs`, `movementMs`, `endpointErrorDeg`, `overshoot`, `holdTremor` |
| **4. Темп/повтор** (ритмичные качания N сек) | плавность, ритмичность, спад от усталости | спастика, выносливость | `smoothnessIndex`, `rhythmicity`, `fatigueDecay` |

> Порядок: покой → диапазон → наведение → темп. От пассивного к активному, от простого к
> нагрузочному (усталость меряем последней). Весь протокол ≈ 60–90 с.

## 3. Как это нормализует дальнейшее обучение и сравнение

Пользователь просил: «ухватить дрожь/аномалии в калибровке, чтобы под них нормализовать
дальнейшее обучение и сравнивать относительно этого». Механика:

1. **Персональный пол тремора.** `restTremorPower` из суб-теста 1 = собственный уровень дрожи
   ребёнка в покое. Порог аномалии тремора в игре считается **сверх этого пола**, а не от нуля —
   ребёнок с дискинезией не флагается «трясётся» на каждой сессии.
2. **Персональный ожидаемый ROM.** `rollRom`/`pitchRom` из суб-теста 2 задают 100% личного
   диапазона. Прогресс в играх меряется в % от него (уже частично есть в `compute_deltas`).
3. **Персональная асимметрия.** `rangeAsym` из калибровки = стартовая асимметрия гемипареза.
   Дальше смотрим **изменение** асимметрии, а не абсолют (у гемипареза она всегда высокая).
4. **Точность как якорь.** `endpointErrorDeg`/`reactionMs` — база для когнитивно-моторного прогресса.
5. **В ML:** профиль калибровки идёт в датасет как **контекст пациента** (рядом с диагнозом/MACS
   в выгрузке `/admin/export/ml-dataset`). Модель может нормировать признаки сессии на профиль
   (session − calibration) → «отклонение от личной сигнатуры», а не абсолютные значения. Это
   честнее для ДЦП, где абсолюты между детьми несопоставимы.

## 4. Схема данных

Новое опциональное поле на `Patient` (не ломает старые карточки):

```jsonc
calibration_profile: {
  "game1": {
    "rest":      { "tremorPower": 0.03, "tremorFreqHz": 4.2, "noiseFloorDeg": 0.6 },
    "rom":       { "rollMin": -38, "rollMax": 41, "rollRom": 79,
                   "pitchMin": -22, "pitchMax": 25, "pitchRom": 47, "rangeAsym": 0.12 },
    "targeting": { "reactionMs": 640, "movementMs": 1180,
                   "endpointErrorDeg": 4.1, "overshoot": 0.18, "holdTremor": 0.05 },
    "tempo":     { "smoothnessIndex": 0.71, "rhythmicity": 0.68, "fatigueDecay": 0.14 },
    "capturedAt": "2026-07-15T...", "inputSource": "ble",
    "quality": { "restStable": true, "romComplete": true, "targetingHits": 5 }
  }
}
```

- Сырые ряды каждого суб-теста по-прежнему пишутся в сессию (`imu_time_series`) — ничего не теряем.
- `baselines[game]` (v1) остаётся для обратной совместимости; `calibration_profile` — расширение.
- Метрики суб-тестов считаются **на клиенте** (как сейчас `targets`), т.к. зависят от позиций
  мишеней/таймингов, не выводимых из сырого ряда. Тремор покоя — через тот же спектральный
  анализ, что в `features.py` (перенести в общий util или считать на сервере из ряда суб-теста 1).

## 5. Что работает СЕЙЧАС, а что ждёт железа (честно)

| Часть | Готово без девайса? | Комментарий |
|-------|---------------------|-------------|
| ROM, асимметрия, точность, реакция, endpoint-error | ✅ (и с клавиатурой) | амплитудные/временны́е метрики достоверны |
| Тремор покоя/интенционный (частота/мощность) | ⚠️ **ждёт A7** | рваный BLE-тайминг искажает частотные признаки; проверять панелью тайминга рекордера |
| Нормализация ML на профиль | ✅ спроектировать, ⏳ обучать | не трогать модель, пока нет реальных размеченных сессий |

> Вывод: **интерфейс и амплитудно-точностные суб-тесты можно строить и тестировать уже сейчас**
> (клавиатура + датчик). Тремор-часть включаем как «сырьё пишем, метрику показываем осторожно»
> до фикса прошивки.

## 6. Открытые вопросы (сверить с реабцентром)

- Какие из 4 суб-тестов **клинически осмысленны** и посильны детям с ДЦП по MACS-уровням? (§7C)
- Приемлемая **длительность** протокола для ребёнка (60–90 с не много?).
- Нужна ли **ре-калибровка** и как часто (смена датчика, курс реабилитации, рост ребёнка)?
- Стоит ли **направляемый темп** (метроном/дыхание) в суб-тесте 4 или свободный?

## 7. Порядок реализации (после сверки с центром)

1. Расширить `Calibration.jsx`: 4 суб-теста, клиентские метрики каждого, запись рядов посуб-тестно.
2. Добавить `Patient.calibration_profile` (опц.) + запись в `set_baseline_from_session` / новый роут.
3. Общий спектральный util тремора (переиспользовать логику `features._spectral_tremor`).
4. Отобразить профиль врачу (`PatientDetail.jsx`) как «сигнатуру» + дельты от неё.
5. В выгрузку `/admin/export/ml-dataset` добавить `calibration_profile` как контекст пациента.
6. Тесты: клиентские метрики суб-тестов (vitest), запись профиля (api), паритет тремора не сломан.

> Реализацию НЕ начинаем до: (а) сверки суб-тестов с реабцентром, (б) решения по тайминг-части.
> Амплитудно-точностный костяк (суб-тесты 1–3 без частотной дрожи) — кандидат на первую итерацию.
