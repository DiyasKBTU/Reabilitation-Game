# ML-конвейер: от сырых данных до модели — регламент

> Как во время ML-теста данные превращаются в модель: кто что делает, какими командами,
> какие ворота качества и когда модель можно (и когда нельзя) выкатывать в прод.
> Конвейер отрепетирован end-to-end 2026-07-14 (без промоута модели).
>
> Связанные документы: `ML_CONTRACT.md` (формат данных), `WORK_PLAN.md` (фаза «Готовность
> к ML-тесту»), `TECHNICAL.md §3` (API). Последнее обновление: 2026-07-14.

---

## 1. Схема конвейера

```
Пациент играет с датчиком (Chrome/Edge, HTTPS)
  └─> POST /sessions: сырой ряд imu_time_series + input_source=ble
        └─> Mongo `sessions` (гарды: не-датчик не идёт в baseline/рейтинг/обучение)

Разметка (ground truth):
  • пациент — на экране результата: боль 0–2, усталость 1–10  → label.pain / label.fatigue
  • врач — в карточке пациента, вкладка «Сессии»: оценка 1–5   → label.quality

Мониторинг: админка → панель «Сбор ML-данных» (/admin/dataset-stats)
  «Готово: норма / аномалия» = ровно то, что возьмёт обучение

Обучение (ЛАБОРАТОРИЯ, не прод):
  cd ml-service && ../venv/Scripts/python.exe -m app.train
    mongo_loader: только input_source ble/None + однозначная метка
      (боль ≥1 или усталость ≥7 → аномалия; боль 0 и усталость ≤4 → норма;
       усталость 5–6 без боли — серая зона, отбрасывается)
    + Mendeley (реальная норма запястья) + синтетика для баланса
  → ml-service/app/models/anomaly_model.joblib   (лабораторная копия)
  → ml-service/data/dataset_latest.npz + dataset_latest_report.json (аудит состава)
  → честные метрики на отложенных 25% + CV

Промоут в прод (ТОЛЬКО вручную, после ревью — раздел 5):
  копия ml-service/app/models/*.joblib → api/app/ml/models/ + CHANGELOG + rebuild api
```

Оценка врача (`quality`) в обучение аномалий сейчас НЕ идёт — это экспертный сигнал,
он сохраняется в label и уходит в выгрузку `/admin/export/ml-dataset` (пригодится для
будущей экспертной модели и для проверки согласия «самочувствие ↔ взгляд врача»).

## 2. Роли и ритм во время ML-теста

| Кто | Что делает | Когда |
|-----|-----------|-------|
| Пациент/тестировщик | Играет с датчиком; на экране результата честно отмечает боль/усталость (это 30 секунд) | Каждая сессия |
| Врач (или вы в роли врача) | В карточке пациента ставит оценку 1–5 свежим сессиям | 1–2 раза в неделю |
| Админ (вы) | Смотрит панель «Сбор ML-данных»: растут ли «Готово: норма/аномалия», нет ли перекоса | Еженедельно |
| ML-инженер (вы) | Прогон обучения → сравнение метрик с прошлым прогоном → запись результатов | Еженедельно, при ≥10 новых размеченных |

Ритм недели: собрали → разметили → посмотрели панель → прогнали обучение → записали
метрики в WORK_PLAN. Модель НЕ промоутится каждую неделю — только по воротам раздела 5.

## 3. Команды

```powershell
# Что лежит в Mongo (источники, ряды, метки) — консольная сводка
venv\Scripts\python.exe api\scripts\inspect_sessions.py

# Только загрузчик: сколько сессий возьмёт обучение прямо сейчас
cd ml-service; ..\venv\Scripts\python.exe -m data.mongo_loader

# Полный прогон обучения (лаборатория; прод не трогает)
cd ml-service; ..\venv\Scripts\python.exe -m app.train

# Паритет признаков + тесты загрузчика (обязательно после любых правок ml-service)
venv\Scripts\python.exe -m pytest ml-service/tests -q
```

Выгрузка датасета для анализа вне сервера: админка → «Скачать датасет (JSON)»
(или `GET /admin/export/ml-dataset`, с сырым рядом — `?include_series=true` порциями).

## 4. Ворота качества ДАННЫХ (когда обучение имеет смысл)

Ориентиры (не догма — здравый смысл важнее):

- **Минимум для первого осмысленного прогона:** ≥30 размеченных датчиковых сессий,
  из них ≥8 аномалий (боль/высокая усталость). Меньше — прогон «для проверки трубы»,
  выводов о качестве не делать.
- **Баланс:** если аномалий <10% — модель учится на синтетических аномалиях,
  честно считать её прежней (synthetic-аномальной).
- **Источник:** только `input_source=ble` (гард стоит в mongo_loader и в панели);
  клавиатурные прогоны в датасет не попадают by design.
- **Качество ряда:** пока прошивка не чинена (рваный BLE-тайминг), скоростным/тремор-
  признакам сырого потока доверять осторожно; ROM/амплитуда надёжны. После фикса
  прошивки — перезамер рекордером (`/tools/imu-recorder/`, панель тайминга).
- **Один источник правды:** реальные данные собираются на ПРОДЕ (HTTPS, один сервер);
  локальная база — только разработка. Не разрывать датасет между базами.

## 5. Ворота ПРОМОУТА модели в прод (все — вручную, все обязательны)

1. **Метрики не хуже прошлой модели** на отложенной выборке (сравнить с прошлым прогоном
   и с текущей прод-моделью: ROC-AUC, confusion matrix, важности — нет ли деградации).
2. **Состав датасета осмыслен:** открыть `dataset_latest_report.json` — сколько реальных
   меток, сколько синтетики. ⚠ Флаг `validation=self-reported` включается даже от ОДНОЙ
   размеченной сессии — смотреть на ЧИСЛА (`n_normal`/`n_anomaly` реальных), не на флаг.
3. **Паритет-тесты зелёные:** `pytest ml-service/tests` (10) — признаки api ≡ ml-service.
4. **Копия обоих файлов:** `ml-service/app/models/anomaly_model.joblib` →
   `api/app/ml/models/anomaly_model.joblib` (pattern-модель — только если переобучалась).
5. **CHANGELOG:** версия, метрики, источник данных, число реальных меток (правило CLAUDE.md).
6. **Проверка на живом api:** перезапуск → `GET /api/health` показывает новую
   `model_version` → одна тестовая сессия проходит без падения в rule-fallback.
7. **Откат** = `git checkout <prev> -- api/app/ml/models/anomaly_model.joblib` + перезапуск.

## 6. Что НЕ делать

- **Не промоутить автоматически** — прогон обучения ≠ новая прод-модель.
- **Не менять пороги z-score в `anomaly.py`** (1.5σ/2.5σ) без реальных данных ДЦП —
  проверено на Неделях 2–3: подъём порогов теряет ранний мягкий регресс.
- **Не заявлять клиническую точность** по ROC-AUC: метки самочувствия — это self-reported
  ground truth, не клиническая валидация; синтетические аномалии легко отделимы
  (ROC-AUC ~1.0 — свойство генератора, не модели).
- **Не собирать метки к клавиатурным сессиям** (веб и так не собирает — не «чинить»).
- **Не переобучать pattern-модель** на этих данных — у неё классы из генератора,
  для неё нужен отдельный план с врачебными метками паттерна.

## 7. Известные ограничения цикла (на 2026-07-14)

| Ограничение | Влияние | Статус |
|---|---|---|
| Рваный BLE-тайминг устройства (пачки + провалы до ~1 с) | Скорость/рывок/тремор по сырому потоку недостоверны; игра пишет 25 Гц с равномерным временем — маскирует | Фикс делегирован (прошивка); проверка — панель тайминга рекордера |
| Реальных аномалий ДЦП в открытых датасетах нет | Аномалии в датасете — синтетика, пока не накопим свои метки | Закрывается этим тестом |
| PAMAP2 авто-загрузка закрыта (ucimlrepo не отдаёт id=231) | Источник опционален; вручную ~1.6 ГБ при желании | Принято, не блокер |
| Метки самочувствия субъективны (ребёнок) | Шум в ground truth; смягчается серой зоной и оценкой врача рядом | По дизайну |
