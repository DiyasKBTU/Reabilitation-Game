# RehabGame — ML/AI спецификация (план реализации)

> Статус: спецификация (код по этому документу ещё не написан).
> Принцип: **измерение — детерминированное и своё; объяснение — можно через LLM.**
> Число (ROM, tremorIndex) никогда не считает языковая модель — только аудируемый код.

## 2. Целевая архитектура

```
                ┌─────────────── ДЕТЕРМИНИРОВАННОЕ ЯДРО (своё, аудируемое) ───────────────┐
imu_time_series │  features.py → anomaly.py (z-score baseline + ML-модель) → recommendations.py │
   (BLE/Firebase)└───────────────────────────────┬──────────────────────────────────────────┘
                                                  │ структурированный JSON (числа, флаги, план)
                                                  ▼
                        ┌──── СЛОЙ ОБЪЯСНЕНИЯ (опционально, фиче-флаг) ────┐
                        │  LLM-explainer  ── провайдер абстрагирован ──    │
                        │  (OpenAI / Claude / локальная)                   │
                        │  ВХОД: только посчитанные числа                  │
                        │  ВЫХОД: текст для врача/пациента                  │
                        │  FALLBACK: шаблонный текст без LLM               │
                        └──────────────────────────────────────────────────┘
```

Гарантия совместимости: LLM-слой меняет только текстовые поля; структура ответа
`/api/insights` (см. `docs/ML_CONTRACT.md`) остаётся неизменной.

## 3. Спецификация компонентов

### 3.1 Feature engine — оставить как есть
- Не менять без запуска `ml-service/tests/` (после починки теста, §4).
- При изменении — синхронизировать `api/app/ml/features.py` ↔ `ml-service/app/features.py`.

### 3.2 Персональный baseline (z-score) — сделать основным «AI»
- Уже работает; повысить в продуктовой подаче как главный механизм.
- Требование: ≥3 валидных сессий пациента (`MIN_BASELINE`). Для нового пациента —
  показывать статус `insufficient_baseline`, а не пустоту.

### 3.3 Обученная модель — переобучить честно — ВЫПОЛНЕНО (v8.2)
- **Сделано:** переобучена → `v5-2026-06-08-synthetic`; в `joblib` добавлены `validation:"none"`,
  `synthetic_only:true`, `metrics_note`; `/api/ml/health` их отдаёт; доки синхронизированы.
- **Маркировка:** `model_version` несёт суффикс `-synthetic`, пока нет реальных данных.
- **Запрет (в силе):** не подавать ROC-AUC на синтетике как метрику качества во внешних материалах.
  Внешняя метрика появляется только после §6 (клиническая валидация).

### 3.4 LLM-explainer — РЕАЛИЗОВАН (v8.3), provider за фиче-флагом
- **Сделано:** `api/app/ml/narrative.py` (шаблон по умолчанию + OpenAI/Claude через `urllib`),
  поле `narrative` в `/api/insights`, карточка «Клиническое заключение» в дашборде, env-конфиг.
  По умолчанию `LLM_ENABLED=false` → детерминированный шаблон (без ключа/сети). Включение —
  выставить ключ и провайдера. **Остаётся:** при клиническом проде — Azure OpenAI/on-prem (152-ФЗ).
- **Назначение:** (а) клинический нарратив врачу из `features+anomaly+trends`;
  (б) поддерживающее сообщение пациенту; (в) опционально «вопрос-ответ по данным пациента».
- **Контракт промпта (жёсткий):**
  - Системный промпт: «Ты переводишь УЖЕ ПОСЧИТАННЫЕ числовые показатели в текст.
    Запрещено вводить новые числа, диагнозы и клинические утверждения, которых нет во входе.
    Если данных нет — так и скажи.»
  - Вход: только структурированный JSON из ядра (никакого сырого IMU).
  - Выход: короткий абзац + список из ≤3 действий, на русском.
- **Провайдер абстрагирован:** интерфейс `LLMProvider.generate(system, payload) -> str`
  с реализациями `OpenAIProvider`, `ClaudeProvider`, `NullProvider` (шаблон). Переключение — env.
- **Fallback:** при ошибке/таймауте/выключенном флаге — детерминированный шаблон из тех же чисел.
- **Экономика (ориентир):** нарратив ≈ сотни токенов. `gpt-4o-mini` ≈ $0.15/1M вход,
  $0.60/1M выход → доли цента за сессию; тысячи сессий/мес = единицы $. (Claude Haiku — сопоставимо.)
- **Приватность (критично, медданные):**
  - PHI к третьей стороне → для клиники нужен Azure OpenAI + BAA, либо локальная модель.
  - Рынок РФ/РК: учесть **152-ФЗ / локализацию данных** — данные граждан хранить в стране.
  - Минимизация: в LLM отправлять только обезличенные числа (без ФИО/идентификаторов).
- **Env-переменные (добавить в `api/.env.example` и `docs/TECHNICAL.md` §6):**
  `LLM_ENABLED`, `LLM_PROVIDER` (openai|claude|none), `LLM_MODEL`, `LLM_API_KEY`, `LLM_TIMEOUT_SEC`.

## 5. Интеграция реальных данных из Firebase — ПОДКЛЮЧЕНО К ПАЙПЛАЙНУ (v8.4) + КРИТИЧЕСКАЯ НАХОДКА

Адаптер `ml-service/data/firebase_loader.py` написан и проверен на реальном экспорте
(`esp-project-fca3d-default-rtdb-export.json`): 1 пациент (Serjan, 20), 3 сессии.

**Реальная схема экспорта (подтверждена):**
- `app_patients/{pid}` — пациент (fullName, age, diagnosis, doctorId).
- `app_sessions` / `rehab_sessions[_by_patient]` — сессии с АГРЕГАТАМИ:
  `rangeOfMotion, maxAngle, minAngle, movementCount, strengthIndex, enduranceSec,
  score, durationSec, level, gameType` + один финальный снимок `roll/pitch/yaw`.
- `ai_data/by_patient/{pid}/{sid}` — один снимок углов на сессию (НЕ ряд).

**КРИТИЧЕСКАЯ НАХОДКА: в экспорте НЕТ сырого временного ряда IMU.**
Из агрегатов вычислимы только 3 геометрических признака: `rom (=rangeOfMotion), minAngle, maxAngle`.
9 признаков (`peakVelocity, meanAbsVelocity, meanJerk, smoothnessIndex, tremorIndex,
symmetryIndex, pauseRatio, repetitions, activeTimeSec`) требуют ряда `[{t,r,p,y},...]` и
**не вычислимы**. Косвенный признак: `movementCount≈3650` за 63 с ⇒ устройство снимает ~58 Гц,
но поток не сохраняется — пишется только агрегат. Реальный результат прогона адаптера:

```
game     score    rom    min    max  dur,s  moves  valid
game2     1450   73.6  -39.9   33.7    63    3650   True
game2      484   60.3  -28.6   31.7   320     875   True
game1        3    0.0    0.0    0.0    14       0  False   ← Space Catcher не пишет угол (см. находку #4)
```

**Что это значит для стратегии:**
1. **СДЕЛАНО (v8.4):** импорт агрегатных сессий в MongoDB — `api/app/ingest/firebase.py` +
   CLI `api/scripts/import_firebase.py` (файл-экспорт или live-URL, идемпотентно по `source`+`source_id`).
   Сессии получают `features.partial=True` + `missing[...]`; ML по ним работает в rule-режиме (z-score
   по ROM), model-режим принудительно отключён (иначе нули вместо 9 признаков → мусорный score).
   Дашборд показывает реального пациента (KPI/норма по ROM, асимметрия по min/max).
2. **Главное (разблокирует богатые признаки и реальную модель):** логировать в `web_game_esp32`
   ПОЛНЫЙ ряд `[{t,r,p,y},...]` рядом с агрегатами, а не только агрегат. Тогда `extract_features()`
   даст все 12 признаков и появится материал для реальной модели/валидации (§6). Минимальный сниппет:

   ```js
   // web_game_esp32: копим ряд во время игры и сохраняем вместе с агрегатами
   const imu = []; const t0 = performance.now();
   function onImuSample(roll, pitch, yaw) {            // вызывать на каждый семпл IMU
     imu.push({ t: Math.round(performance.now() - t0), r: roll, p: pitch, y: yaw });
   }
   // при завершении игры — сохранить ряд вместе с агрегатами:
   await saveSession({ ...aggregates, imuTimeSeries: imu });   // → 12 признаков на бэкенде
   ```
3. Игра `game1` (Space Catcher) в проде не пишет угол (ROM=0) — чинить как finding #4 (синтез roll).

## 6. Клиническая валидация (превращает заглушку в реальный AI)
- Замкнуть flywheel: эндпоинт/джоба переобучения по накопленным `(features, label)` из сессий.
- Метрика качества считается **только** на реальных размеченных данных (hold-out по пациентам,
  чтобы не было утечки между сессиями одного пациента).
- Зафиксировать в `docs/CHANGELOG.md`: версия модели, источник, честные метрики, дата.
- Цель пилота: ≥N пациентов × ≥M сессий с метками; целевые метрики согласовать с клин. партнёром.
