## ML — 2-осевой анализ аномалий (roll + pitch) для City Driver (2026-06-18)

### Суть
City Driver управляется двумя осями (руль = roll, газ/тормоз = pitch), но вердикт строился
только по roll — отклонение в оси газ/тормоз (напр. тремор при сгибании/разгибании) врач не видел.
Теперь анализируются ОБЕ оси, вердикт агрегируется, и врачу видно, какая ось отклонилась.

### Ключевое решение: без переобучения модели
`extract_features(series, axis)` и модель **axis-agnostic** — один и тот же 16-мерный вектор по
любой оси. Значит «переобучение на 2-осевой синтетике» теми же профилями дало бы идентичную модель
(no-op). Настоящая работа — оркестрация по осям, а не модель. Паритет `features.py` не затронут.

### Сделано
- `api/app/ml/games.py`: единый источник `ANALYZED_AXES` (game2 → roll + pitch как анализируемые).
  `axis_for_game`/`secondary_axes_for_game`/`GAME_AXIS`/`SECONDARY_AXES` — производные (совместимость).
- `api/app/ml/multiaxis.py` (новый) — `analyze_axes()`: детект по каждой оси → агрегат
  (status = худшая ось, anomalyScore = максимум, флаги помечены `axis`/`axisLabel`, `leadAxis`).
- `api/app/routes/insights.py`: пер-осевой current+history (для pitch — из `axis_features`,
  бэкфилл на лету), оркестратор вместо одноосевого `detect_anomalies`; `axis_features[ax]` теперь
  несёт собственный `anomaly`. recommendations/narrative — по основной оси + общий вердикт.
- `api/app/routes/sessions.py`: `mark_validity` и для вторичных осей (idle-pitch не в baseline).
- `web/src/pages/PatientDetail.jsx`: карточка «Вторая ось» с пер-осевым `AnomalyBadge`; флаги в
  алерте помечены осью. Текст «не входит в оценку аномалий» убран.
- `docs/ML_CONTRACT.md` §2/§4, `docs/TECHNICAL.md` — обновлены под multi-axis ответ.

### Проверка
- `api/tests/test_multiaxis.py` (новый) — 4 теста агрегации (худший статус, ведущая ось, пометка
  осей, обратная совместимость одноосевой игры). api/tests → 15 passed; ml-service → 10 passed (паритет).
- Сквозная проверка на реальной модели: тремор 6 Гц ТОЛЬКО в pitch → roll=normal, pitch=critical,
  общий=critical, `leadAxis=p`. Старая roll-only модель этот тремор пропускала. `npm run build` зелёный.

## ML — фикс train/serve skew: запись IMU-ряда 25 Гц + несглаженный угол (2026-06-18)

### Проблема
Модель аномалий обучена на синтетике **25 Гц** (`fs_hz=25`), где два самых важных признака —
спектральные `tremorPower` (~0.21) и `tremorFreqHz` (~0.18). Но игры писали ряд на **5 Гц**
(аккумулятор 200 мс) и притом **дважды сглаженный** (EMA в BLE → второй EMA в движке). При
5 Гц Nyquist = 2.5 Гц < нижней границы полосы тремора 3 Гц → `_spectral_tremor` структурно
возвращает `(0, 0)`, а EMA-сглаживание гасит тремор 4–8 Гц ещё до записи. Итог: ~40% «важности»
модели в продакшене мертвы — детектор тремора не мог сработать ни на одной реальной сессии.

### Сделано (только захват данных — модель НЕ переобучалась)
- `packages/ble/index.js`: событие `data` теперь несёт `calib` (калиброванный, но **несглаженный**
  угол) рядом со `smooth` (управление) и `raw` (диагностика). Аддитивно; UUID/команды/прошивка
  не изменены.
- `packages/game-2d/index.js`, `packages/game-3d/index.js`: отдельный канал записи `_rec*`
  (несглаженный) пишется в `imu_time_series` вместо `_smooth*`; частота записи 5 → **25 Гц**
  (`IMU_RECORD_MS=40`, Nyquist 12.5 Гц покрывает полосу тремора). Без устройства (клавиатура/демо)
  пишется синтез-угол как раньше (тремора там нет). `updateInput()` принял 4-й арг `rec`.
- `web/src/pages/Game2D.jsx`, `Game3D.jsx` и оба `demo.html`: прокинут `e.detail.calib` в запись.

### Проверка
- Доказательство на тремор-сигнале (медленное движение 0.4 Гц + тремор 6 Гц) через
  `extract_features`: **5 Гц** → `tremorFreqHz=0, tremorPower=0, tremorIndex=0`; **25 Гц** →
  `tremorFreqHz=6.0` (частота определена точно), `tremorPower=0.694`, `tremorIndex=0.773`.
- `pytest ml-service/tests/` → 10 passed (паритет `features.py` не затронут). `npm run build` зелёный.
- Осталось: подтверждение на железе ESP32 (нейтральная поза R/P/Y ≈ 0, тремор виден в признаках).
  Размер ряда вырос ×5 (60 с ≈ 1500 семплов) — приемлемо для Mongo.

## v8.8 — Калибровка старта игры: «ноль = текущая поза кисти» (2026-06-10)

### Проблема
При игре с устройством платформа/машина в начальной позиции слегка «уезжала»: EMA в
`BleService` копит угол ещё до старта, а базовый наклон датчика в нейтральной позе ≠ 0.

### Решение (только клиент, без правок прошивки)
- `packages/ble/index.js`:
  - новый метод `zeroNow()` — клиентский ноль: текущая сырая поза становится нулём
    (`*Offset = текущие углы`), EMA сбрасывается. Без команды устройству → нет задержки и
    конфликта с аппаратным `CALIB`.
  - `_handleData()` вычитает offset ДО сглаживания; `data.smooth` теперь откалиброван,
    `data.raw` остаётся истинными показаниями датчика.
  - `calibrate()` (аппаратный `CALIB`) сбрасывает клиентский offset — чтобы устройство и
    клиент не обнуляли позу дважды.
- `web/src/stores/bleStore.js` — проброс `zeroNow()`.
- `web/src/components/GameIntro.jsx` — при «Начать» (если подключено устройство) вызывается
  `zeroNow()`, затем старт.
- UUID / команды / события BLE НЕ изменены → синхронизация с прошивкой ESP32 не требуется.
- Проверено: `cd web && npm run build` — 874 модуля, 0 предупреждений.

## v8.7 — Гард «пустых прогонов»: мусорные сессии не доминируют в аналитике (2026-06-10)

### Проблема
Если игру (Game2D/Game3D) запустить и не управлять, машина/платформа разбивается,
срабатывает `onGameOver` и сохраняется сессия с ROM≈0 и почти нулевыми признаками. Как
самая свежая (`sessions[0]`) она доминировала в `GET /api/insights` и давала ложный
вердикт «Критично» в дашборде врача (`PatientDetail.jsx`).

### Решение (бэкенд, без удаления сырых данных)
- `api/app/ml/validity.py` (новый) — слой поверх вектора признаков (не трогает `features.py`,
  паритет с `ml-service` сохранён, 5 тестов зелёные):
  - `mark_validity()` — на записи снимает `valid` у сессий без движения
    (`ROM < 5°` ИЛИ `sampleCount < 10` ИЛИ `durationSec < 3`);
  - `is_analyzable()` — на чтении отбраковывает такие сессии (в т.ч. ретроспективно — старые
    с `valid=True`, ROM≈0). Частичные признаки Firebase (ROM-only) не задеты.
- `api/app/routes/sessions.py` (`POST /sessions`) — помечает невалидные сессии; сырой
  `imu_time_series` сохраняется (CLAUDE.md: сырые данные не удалять).
- `api/app/routes/insights.py` (`GET /insights`) — `latest` = первая ВАЛИДНАЯ сессия (а не
  `sessions[0]`); baseline аномалий и тренды считаются только по валидным. Нет валидных →
  пустой ответ (дашборд показывает «нет данных движения», а не ложный вердикт).
- Логика зеркалит `ingest/firebase.py` (game1 с ROM=0 → `valid=False`).
- Демо-вердикты не затронуты: «Критично» там — реальная сессия (ROM=12, боль), не пустой прогон.
- Доки: `docs/TECHNICAL.md` §3 (Sessions + insights), §5 (валидность сессии).

## v8.4 — Мост Firebase → MongoDB: реальные данные уходят в ML (2026-06-08)

### Импорт Firebase RTDB → MongoDB (приоритет ML_SPEC §5/§7, п.2)
- `api/app/ingest/firebase.py` — чистый нормализатор экспорта RTDB (или ответа REST `<db>/.json`)
  в пациентов/сессии RehabGame. Из агрегатов строит ЧАСТИЧНЫЕ признаки (rom/minAngle/maxAngle,
  `partial=True`, `missing[...]`); сессии game1 с ROM=0 помечаются `valid=False`. Понимает плоскую
  (`rehab_sessions`/`app_sessions`) и вложенную (`rehab_sessions_by_patient`) формы.
- `api/scripts/import_firebase.py` — CLI: импорт из файла-экспорта ИЛИ live-URL базы, идемпотентно
  (ключ `source`+`source_id` — повторный запуск не плодит дубли). Флаги `--dry-run` (предпросмотр
  без БД) и `--doctor-id` (привязка пациентов к врачу — при повторном запуске обновляет привязку
  уже существующего пациента, чтобы связать данные с врачом постфактум). Чтение через utf-8-sig (снимает BOM).
- Модели: `Session` получил `device_metrics` (strengthIndex/movementCount/enduranceSec/снимок углов)
  и `source`/`source_id`; `Patient` — `source`/`source_id`. Поля опциональны → существующие данные не ломаются.

### Реальный импорт выполнен и проверен end-to-end
- Импортирован реальный экспорт `esp-project-fca3d-default-rtdb-export.json`: 1 пациент (Serjan, 20),
  3 сессии (2 валидные game2 ROM 73.6°/60.3°, 1 невалидная game1 ROM=0). Дубли в экспорте
  (`app_sessions`/`rehab_sessions`/`..._by_patient`) НЕ задваиваются — нормализатор берёт один источник.
- Идемпотентность подтверждена на реальных данных (повтор → +0 пациентов, +0 сессий).
- ML-путь `/api/insights` прогнан на импортированных данных: `mode=rule`, `partial=True`,
  `status=insufficient_baseline` (2<3 валидных), `sessionPlan.levelAdvice=hold` (без ложного «decrease»),
  narrative показывает только ROM и помечает «сырой ряд не записан».

### Корректное отображение частичных данных на фронтенде (баг-фикс, зеркало backend)
- `web/src/lib/clinical.js`: `SERIES_DEPENDENT` + `isMeasured()`/`measuredValue()` — зеркало
  `api/app/ingest/firebase.py`. На частичных (Firebase) сессиях признаки, требующие сырого ряда
  (плавность, тремор, скорость, паузы, активное время), = 0 означают «не измерено», а не реальный ноль.
- `web/src/pages/PatientDetail.jsx`: KPI-карточки таких признаков показывают «не измерено · нет сырого
  ряда» (а не «0%» с ложной клинической подсветкой); личная норма и блок «Прогресс» считаются только по
  измеренным значениям; таблица сессий — «—» вместо «0»; добавлена пометка «оценка по амплитуде».
- `web/src/components/SessionChart.jsx`: точки неизмеренных признаков на частичных сессиях не рисуются
  (раньше график плавности/тремора падал в ложный 0). Сборка чистая (`npm run build`).
- Проверено в браузере на реальном Serjan (game2): ROM=60° реален, плавность/тремор/скорость = «не измерено»,
  заключение «Мало данных · персональная норма», план «Сохранить уровень». Скриншот подтверждён.

### Фиксы зависимостей (ломали старт API и авторизацию)

### Корректная деградация ML на частичных признаках (баг-фикс)

## v7.1 — Исправление вырождения признаков smoothnessIndex / tremorIndex (2026-06-05)

### Критический баг

`smoothnessIndex = 0.0` и `tremorIndex = 1.0` для ВСЕХ сессий при частоте дискретизации ≥ 20 Гц.

**Причина:** формулы были откалиброваны под 5 Гц. При 25 Гц шум датчика усиливается в ~(25/5)² = 25× через трёхуровневое дифференцирование.

### Исправления (паритет JS ↔ Python сохранён)

1. **MA(3) сглаживание** перед дифференцированием — снижает шум в ~5× в jerk.
2. **dt-нормализация jerkScale** — `jerkScale *= max(1, (200/dt_avg_ms)²)`.
3. **Новый tremorIndex** — смены направления скорости с адаптивным порогом, оба соседних сэмпла должны превышать порог.

### Результат

| Признак | До (норма/аномалия) | После (норма/аномалия) |
|---------|---------------------|------------------------|
| smoothnessIndex | 0.000 / 0.000 | **0.848 / 0.800** |
| tremorIndex | 1.000 / 1.000 | **0.048 / 0.499** |

### Модель → v4-2026-06-05
- ROC-AUC test: **0.990**, CV: **0.991 ± 0.003**
- tremorIndex importance: 0.000 → **0.130**
- smoothnessIndex importance: 0.000 → **0.033**
