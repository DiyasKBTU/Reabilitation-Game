## Шаг 1 — Калибровка старта ✅ ГОТОВО

Проблема: платформа/машина «уезжала» в начальной позиции (EMA копит угол до старта + базовый
наклон датчика ≠ 0).

Сделано (v8.8, см. CHANGELOG):
- `packages/ble/index.js`: `zeroNow()` (клиентский ноль), offset вычитается до сглаживания,
  `calibrate()` сбрасывает offset.
- `web/src/stores/bleStore.js`: проброс `zeroNow()`.
- `web/src/components/GameIntro.jsx`: «Начать» → `zeroNow()` (если подключено) → старт.
- Сборка зелёная. Прошивку править не нужно (UUID/команды/события не менялись).

Проверка с железом (когда будет ESP32): подключить, наклонить кисть, нажать «Начать» —
платформа должна стартовать по центру; в нейтральной позе R/P/Y в BLE-панели ≈ 0.

## Шаг 2 — Модель на реальных данных 🔄 В РАБОТЕ

### Решение пользователя (2026-06-10)
Выбраны все три источника. Приоритет — **данные вашего устройства** (где лежат — пользователь
не знает; «если в Монго, то с него»). PAMAP2 учесть как улучшение. Сырой ряд писать — да.

### Сделано (2.1 — мост «данные устройства → датасет»)
- `ml-service/data/mongo_loader.py` (новый): тянет сессии с сырым рядом из Mongo и выводит
  РЕАЛЬНУЮ метку нормы/аномалии из оценки пациента (`label.pain`/`label.fatigue`) — ground truth.
  При выключенной Mongo возвращает пусто, не роняя обучение.
- `ml-service/app/train.py`: Mongo — приоритетный источник; сохранение нормализованного
  датасета `data/dataset_latest.npz` + `dataset_latest_report.json`; честная версия
  `v7-2026-06-10-realdata-*` и `validation` ("self-reported", если есть метки устройства).
- `ml-service/tests/test_mongo_loader.py`: 5 тестов (логика метки + graceful при Mongo down).
- `api/scripts/inspect_sessions.py` (новый): показывает, что лежит в Mongo (источники, сколько
  с сырым рядом). Сейчас Mongo выключена → запустить, когда поднимете БД.
- Проверено: `pytest ml-service/tests/test_mongo_loader.py ml-service/tests/test_parity.py` →
  10 passed; `py_compile` train.py/mongo_loader.py OK.

### 2.2 — обучение на реальном IMU (PAMAP2): ⛔ АВТО-ПУТЬ ЗАКРЫТ
- Найден и исправлен баг: Windows-консоль (cp1251) роняла emoji-print загрузчика PAMAP2
  (`UnicodeEncodeError` на ⚠/📥), что МОЛЧА откатывало обучение на синтетику. Фикс: stdout/stderr
  → utf-8 в `train.py` (закоммичено в изменениях train.py).
- После фикса видна НАСТОЯЩАЯ причина: **PAMAP2 (id=231) недоступен для импорта через
  `ucimlrepo`** — UCI не отдаёт этот датасет через Python API. Авто-загрузка невозможна.
- Единственный путь PAMAP2 — РУЧНАЯ загрузка (по решению пользователя, ~1.6 ГБ):
  1) скачать zip с https://archive.ics.uci.edu/dataset/231 ;
  2) распаковать `Protocol/*.dat` в `ml-service/data/pamap2/` ;
  3) `cd ml-service && ../venv/Scripts/python.exe -m app.train` (loader подхватит локальные .dat).
- Модель НЕ изменена: synthetic-only откат восстановлен из git, продакшн-копия в `api/` нетронута.

### 2.3 — обучение на ВАШИХ данных (Mongo): ⏳ ЛУЧШИЙ ПУТЬ, ждёт данных
Инфраструктура готова (мост 2.1). Чтобы получить модель на РЕАЛЬНЫХ данных вашего устройства:
1. Поднять MongoDB (порт 27017).
2. Сыграть несколько сессий через приложение (с ESP32 или на клавиатуре) и на экране результата
   оценить самочувствие (боль/усталость) — это даёт настоящие метки.
3. `venv\Scripts\python.exe api\scripts\inspect_sessions.py` — проверить, что сессии с рядом есть.
4. `cd ml-service && ../venv/Scripts/python.exe -m app.train` — `mongo_loader` сам подхватит
   размеченные сессии; модель обучится на них (+ синтетика для баланса), метрики честные.
5. Ревью метрик → промоут модели в `api/app/ml/models/` → запись в CHANGELOG.

### Ждёт данных (2.3 — ваши реальные сессии)
Как только сыграете через приложение (Mongo запущена) и оцените самочувствие — `mongo_loader`
подхватит эти сессии автоматически при следующем `python -m app.train`. Это и есть «обучение на
данных вашего устройства» с настоящими метками. Проверить наличие: `inspect_sessions.py`.

### Что выяснено (факты по коду)
- **Реальных данных устройства в репозитории НЕТ** (ни Firebase-экспорта, ни PAMAP2, ни
  Mongo-дампа). Текущая модель `anomaly_model.joblib` — `synthetic_only=True`, `validation:none`.
- **Куда пишутся реальные данные:**
  - живая игра с ESP32 → `imu_time_series` (полный ряд) в Mongo, коллекция `sessions`;
  - старое устройство (Firebase RTDB) → **только агрегаты**, без сырого ряда → импорт в Mongo
    как `partial` (3 признака: rom/min/max), `device_metrics`.
- **Прошивка НЕ сохраняет сырой ряд** (в Firebase movementCount≈3650 за 63 с ⇒ поток ~58 Гц
  есть, но не пишется). Поэтому полную 16-признаковую модель на данных устройства обучить нельзя
  без изменения логирования.
- Загрузчики уже есть: `ml-service/data/real_data_loader.py` (PAMAP2),
  `ml-service/data/firebase_loader.py` (агрегаты). Обучение: `ml-service/app/train.py`.

### Варианты источника (нужен выбор пользователя)
- **A. Ваш Firebase-экспорт / реальные Mongo-сессии** (данные именно устройства).
  Минус: из агрегатов только 3 признака, меток боли/усталости нет → можно лишь урезанная
  безнадзорная модель. Нужен: файл экспорта `.json` ИЛИ доступ к Mongo с реально сыгранными
  сессиями (с `imu_time_series`).
- **B. PAMAP2 (реальный IMU запястья, UCI)**: полный ряд → все 16 признаков, `train.py` уже
  поддерживает. Минус: это не ваше устройство, «аномалии» синтетически деградированы (нет
  реальных меток). Нужен: `pip install ucimlrepo` + ~80 МБ загрузки.
- **C. Сначала root-fix**: научить веб/прошивку писать сырой ряд `[{t,r,p,y}]`, затем копить
  реальные размеченные данные устройства. Самый долгий, но единственный путь к настоящей
  device-specific модели с метками.

### Подзадачи Шага 2 (после выбора источника) — выполнять по порядку
1. Загрузка/нормализация выбранного источника → единый формат рядов/признаков.
2. Сборка **нормализованного датасета**: `extract_features` → матрица X, метки y; сохранить
   версионированный артефакт (напр. `ml-service/data/dataset_<src>.npz`) + отчёт о составе
   (число норм/аномалий, диапазоны признаков, источник).
3. Обучение (`train.py` или новый скрипт): RobustScaler + RandomForest(калибр.) + IsolationForest.
4. **Честная оценка**: hold-out test (25%), ROC-AUC, classification_report, confusion matrix,
   CV ROC-AUC, важность признаков. Маркировка `validation` и суффикса версии честно.
5. **Анализ**: дискриминация признаков по профилям (как `analyze_pitch.py`); сравнение новой
   модели со старой синтетической.
6. **Тесты**: pytest, проверяющий, что датасет/модель грузятся, форма ответа `detect_anomalies`
   не сломана, паритет признаков сохранён (`ml-service/tests/`).
7. Доки: CHANGELOG (версия модели, метрики, источник), `ML_SPEC.md` §5–6, `ML_CONTRACT.md` если
   меняется ответ.

> ⚠️ Честная рамка: ROC-AUC на синтетике/деградации ≠ клиническая точность. До реальных меток
> боли/усталости главным механизмом остаётся персональный z-score baseline (Слой 2).
